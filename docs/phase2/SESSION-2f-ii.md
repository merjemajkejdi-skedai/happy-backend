## Implemented

### 1. `src/modules/orders/splitService.ts` — new exports

- `SplitAllocation` — `{ orderItemIds: string[], label?: string | null }`.
- `createChildOrderShell` (private) — the child-order-creation dance shared by `by_item`/`by_seat` (own `order_number`/`ticket_number` via `allocateNumbers`, `parent_order_id`, `split_sequence`). A deliberately separate helper from equal split's inline version in `splitEqual` — not a refactor of that working, tested code, just new code for the new paths.
- `checkAllocationSplitGate` (private) — 404/409 `ORDER_NOT_MODIFIABLE`/403 `SPLIT_MODE_DISABLED` (`split_bill_enabled AND split_by_item_enabled`)/409 `ORDER_ALREADY_PAID`, shared by both entry points so the gate always runs even when there's nothing to split (`by_seat` with zero seated items).
- `moveItemsIntoChildren` (private) — the core mover: creates each child, updates the listed items' `order_id`/`split_from_order_id`/`original_order_item_id` in place (nothing else touched — status, every snapshot, every timestamp survive exactly), recomputes every child and then the parent through the ordinary `recomputeOrder` formula, sweeps the parent for now-empty never-fired `order_courses` rows, and writes one `order.split` event on the parent. One transaction — a failure at any point rolls back every move and every child.
- `splitByItem(venueId, actorUserId, orderId, allocations)` — validates allocation count (`[1, split_max_ways]`, else 422 `SPLIT_WAYS_INVALID`), each allocation non-empty, no item double-allocated (422 `SPLIT_ITEM_DOUBLE_ALLOCATED`), every item belongs to this order (422 `SPLIT_ITEM_NOT_IN_ORDER`), no item cancelled (422 `SPLIT_ITEM_CANCELLED`) — then delegates to `moveItemsIntoChildren`.
- `splitBySeat(venueId, actorUserId, orderId)` — groups the order's active (non-cancelled) items by `seat_number`, skipping items with no seat; zero distinct seats is a no-op success (`{ok: true, value: []}`); more distinct seats than `split_max_ways` is 422 `SPLIT_WAYS_INVALID`; otherwise builds one allocation per seat (ascending) and delegates to the same mover.

## Interpretation calls — flagged explicitly

- **`original_order_item_id` is set once, on an item's first-ever move, and never overwritten again** (`item.originalOrderItemId ?? item.id`). Since items move via an in-place `order_id` update (the row's own `id` never changes), the field's only meaningful job is marking the lineage root the first time a move happens; a later move of the same item just carries the existing value forward.
- **`SPLIT_ITEM_CANCELLED` is a brand-new code, not a reuse of `ITEM_ALREADY_CANCELLED`.** The spec's own validation table wants 422 for this rule, but `ITEM_ALREADY_CANCELLED` is already documented at 409 for voiding (`docs/ERRORS.md`) — reusing it at a different status than its established meaning would make code-based client matching ambiguous. Minted a new code instead, following the session's own `SPLIT_ITEM_*` naming.
- **A `closed`/`cancelled` parent blocks `by_item`/`by_seat` too, and `amount_paid > 0` blocks them too** — neither is restated in 2f-ii.md's own validation table (only the item-level rules are), but both are generic "you can't split a done-with order" properties already established for equal split in 2f-i, applied here for consistency via the shared `checkAllocationSplitGate`.
- **"Drop empty course rows on the parent only if they were auto-created" reads as "only if never fired."** Every `order_courses` row in this codebase is lazily auto-created by `recomputeOrder`'s own course roll-up the instant an item first carries that `course_number` — there is no other creation path, so literally all of them are "auto-created" in that sense. The distinction that actually matters is whether the row carries real history: a row that's empty and was never fired is pure bookkeeping and gets deleted; a row that's empty but WAS fired represents genuine past kitchen activity and is kept regardless of item count. Covered by two dedicated tests (one per outcome).
- **`by_seat` only ever groups active (non-cancelled) items, and never moves a cancelled one.** A cancelled item sitting at seat 3 doesn't drag seat 3's other items into being "seat 3's allocation" by virtue of also having that seat number, and it never becomes an allocation of its own — it simply stays put, same as an item with no seat at all.
- **Tax conservation relies on `recomputeOrder`'s existing per-order-independent formula, not a purpose-built cross-order rounding scheme.** Because the formula sums `line_total × tax_rate_snapshot / 100` per item and each item's tax is unaffected by which order currently holds it, the TRUE (unrounded) sum across parent + children always equals the original — but each order's own total is independently rounded to 2 decimal places on write, so in a pathological case (tax sums landing exactly on a rounding boundary differently per order) the rounded sum across orders could in principle differ from the original by a cent. This mirrors a well-known "sum of rounded parts vs. round of the sum" edge case and was not specially solved — `recomputeOrder` is reused exactly as every other mutation in this codebase already relies on it, and the far more common real bug this session actually guards against (and tests) is simpler: forgetting to recompute the *parent* after items leave it, which would silently double-count moved items' tax across both orders. The test suite uses clean tax numbers (10%) that don't trigger the rounding edge case; flagged here rather than silently assumed away.
- **`merge-back` is unchanged and stays equal-split-only in practice.** It deletes the child order under the assumption that doing so is safe (only a single synthetic line item, cascaded away with it) — running it against a `by_item`/`by_seat` child would hard-delete whatever REAL order items live there. Nothing currently stops a caller from doing this; it's called out explicitly in `docs/API.md` as a known gap rather than silently left undocumented. Reversing an item-level split properly (moving items back rather than deleting them) is follow-up work, not attempted this session.

## Tests

`tests/splitByItem.test.ts` (new, 12 tests): a moved item's status/`sent_at`/every snapshot/`course_number` are byte-for-byte identical before and after, only `order_id`/`split_from_order_id`/`original_order_item_id` change; double allocation rejected; an item from a different order rejected; a cancelled item rejected; disabled mode 403; unallocated items remain on the parent; parent-plus-children `grand_total` conserves exactly across a 2-item, 10%-tax order split into two single-item children; course reconciliation both ways (empty+never-fired parent row dropped, empty+fired parent row kept) plus the child getting its own fresh course row; `by_seat` groups two seated items in ascending seat order and leaves a third, seatless item on the parent; `by_seat` is a no-op success with zero seated items; and a genuine rollback test (same real-constraint technique as 2f-i's) that pre-occupies the second child's predicted `order_number`, forces the transaction to fail after the first item has already been moved, and confirms both items are back on the parent with zero orphaned children.

One real bug caught and fixed by these tests before they went green: `moveItemsIntoChildren` was pushing the pre-recompute child shell (totals still zero) into the returned array instead of the value `recomputeOrder` returns, so callers always saw `grand_total: 0` on every child. Fixed by capturing and pushing `recomputeOrder`'s return value.
